### HV-001 ★ · Cross-niche transfer: give contract-judgment the waking-dream treatment — an execution-probe second view at serve time
- **source:** Contract-judgment is the closest section to a gain: battery 0.9167 (11/12), one item from 1.0, and one section item is worth 1/12 ÷ 8 = +0.0104 on the 0.941 overall. The mechanism that fixes exactly this shape already exists one niche over: on the sealed bug set the raw composer scores 0.4722 while the served verify-by-execution path scores 0.8611 (`factory/reports/e007-retrocheck-2026-11-12.md`) — verification, not voting, is where this hive's accuracy lives. Contract labels are *already* proved by execution at generation time (behavioural signature on None/[]/[3,1,2] probes, `FACTORY-LOOP.md` Phase D), but at serve time the niche answers with the bare TinyNet and no probe ever runs.
- **mechanism:** When the serving contract model's margin is thin (below a dev-fitted threshold), run the niche's own execution-signature probe on the submitted function and let the probe's proved label break the tie / overrule. Thick-margin calls are untouched, so the cost and the blast radius are confined to the calls the model itself is unsure about — the same division of labour as the waking layer (composer proposes, execution disposes), transferred across niches.
- **change:** `factory/serve.py` `ServingHive._serve_impl()` — the classify branch gains a margin-gated probe step for `contract-judgment-model` only, calling the contract execution-signature checker in `factory/dream_gen_niches.py` (the machinery behind `contract_gen_pool()`); threshold fitted on the niche's held/screen pools, never on battery items.
- **judged by:** Battery `classify-contract-judgment` must reach 1.0 (12/12) with every other section unmoved, so overall beats 0.941 (≈0.9514). Probe-on vs probe-off measured in the same battery session; shadow (probe computed, verdict logged, TinyNet still answers) until that run lands.
- **kill test:** On the contract held + screen pools, if the probe's proved label agrees with the TinyNet's *errors* on the thin-margin subset — i.e. probe tie-breaking does not beat TinyNet-alone on held thin-margin items — the miss is not execution-checkable; retire before any battery run.

### HV-002 ★ · Member lifecycle: leave-one-out retire-or-merge audit for the 16-member bug composition
- **source:** The composition carries 16 members (off-by-one ×4, wrong-operator ×5, swapped-operands ×4, mutable-default ×1, missing-return ×2 — `factory/COMPOSITION-RESEARCH.md`) and every recorded serving failure was a margin-scale side effect, not a verdict change: the learned say fell on clean recall (0.8182 → 0.6364) because "combination changes move the verification behaviour" (`factory/reports/learned-say-2026-11-12.md`), and cycles 6/7 repeated the identical signature (clean 0.8182 → 0.6364 / 0.7273) while raw composed totals never moved (0.4722 → 0.4722, e007 retrocheck). No H entry proposes *removing* anything: the factory only ever adds members, and each addition re-rolls the margin scales the waking layer's clean-win gate reads.
- **mechanism:** Measure each member's marginal contribution on the dev pool (the 625-item `compose_research` pool, never sealed): composed accuracy with the member present minus without it, plus its effect on clean recall through the full serving path. A member at ≤ 0 marginal contribution is retired from the composition (file kept as fallback provenance); two members whose margins correlate near-perfectly on dev are merged to one seat. A smaller, load-bearing-only composition shrinks the surface every future birth perturbs.
- **change:** `factory/compose_research.py` `a1_preds()` harness extended with the leave-one-out pass; `factory/dream.py` `load_bug_registry()` / `make_composer()` consume the reduced member list; `factory/registry.py` `build_registry()` records retired members as shadow provenance instead of composition members.
- **judged by:** Dev first: reduced composition must hold dev composed accuracy ≥ the 16-member baseline with clean recall no lower. Then the battery gate: sealed bug slice must hold ≥ 0.8611 and overall must beat 0.941 (a tie at 0.941 with fewer members is reported as a robustness win, not an accuracy win — stated as such). Shadow (dev-only) until the battery run.
- **kill test:** If every member's leave-one-out delta is strictly positive on dev, there is no dead weight to retire — the composition is already minimal at 16; retire the audit and record the negative result.

### HV-003 ★ · The serve log as a training asset: provenance-tagged verified-serve harvest into the dream pool
- **source:** `factory/serve_log.jsonl` now holds 486 lines; of its 78 bug-pattern calls, 66 ended `verified` and 12 `fallback-unverified` (current-log count). A verified answer is an execution-proved label — the exact currency `factory/dream_gen.py` manufactures at cost (628 verified items generated for the Phase C dream cycle, 456 then dropped by the contamination filter to keep 172). Yet `factory/serve.py` `_append_serve_log()` stores only `input_head` (80 chars) and a 16-char `input_sha`: the full input is unrecoverable, no caller provenance is recorded, and battery self-calls are indistinguishable from outside demand — so the log can be *counted* (H-014's mining) but never *trained on* or *replayed*.
- **mechanism:** Two-step: (1) log v2 — for bug-pattern calls, store the full code plus a `caller` tag (battery / growth-cycle / external) so sealed battery items are mechanically excluded from any harvest; (2) harvest — verified, non-battery, contamination-filtered serve pairs enter the dream cycle's pool as a named supply line alongside generated families, with the same execution-verified status the generator items carry (the waking layer already proved them).
- **change:** `factory/serve.py` `_append_serve_log()` — schema v2 fields (`caller`, full `code` for bug-pattern kind); `factory/spawn_mining.py` `mine_serve_log()` gains the harvest export; `factory/dream.py` `run_dream_subject()` accepts the harvested file through its existing contamination + difficulty filters, gates unchanged.
- **judged by:** Supply measure first (honestly labelled): harvested items surviving the contamination filter per 100 external bug-pattern calls. Serving claim only via the normal dream-cycle gates, ending at the battery: sealed slice > 0.8611 contribution, overall > 0.941. No number is claimed for the log change itself.
- **kill test:** After 200 new logged bug-pattern calls, if the harvest yields zero usable items (all battery-tagged, or all contamination-dropped), real serving traffic at this scale produces no training asset — retire the harvest, keep log v2's provenance tag for HV-008's drills.

### HV-004 · Battery design: pin the section set — "overall" is currently the mean of whatever happens to be in the file
- **source:** `factory/status.py` `_battery_overall()` computes the mean of *every* `score` in the results doc it reads. The standing acceptance file (`results/hive_battery_acceptance.json`) has accumulated 16 scored entries — the 8 cycle sections plus hive-b1..b6 at 0.0, `classify-contract-judgment-v3-not-served` at 0.4167, and the shadow say at 0.8056 — whose mean is **0.5469**, while the headline 0.941 is the mean of only the 8 sections a growth cycle writes into its own `battery_after.json`. `run_battery.py` `save()` merges each new entry into the existing doc, so sections persist across runs indefinitely: the same hive has two different "overall" numbers depending on which file a reader happens to open, and any future section added to the acceptance file silently redefines the headline.
- **mechanism:** Define the headline once: a `BATTERY_SECTIONS` constant naming the exact sections that constitute the serving battery; overall is the mean over exactly those, computed identically everywhere, with all other entries reported as annexes (composites, shadows, not-served probes) that can never enter or leave the mean by accumulation.
- **change:** `factory/run_battery.py` — add `BATTERY_SECTIONS` and compute the headline in `save()`; `factory/status.py` `_battery_overall()` and `factory/growth_cycle.py` `measure_served_battery()` both consume that constant instead of averaging doc contents.
- **judged by:** Replay check: recomputing every recorded cycle battery (006/007 included) under the pinned definition must reproduce their recorded before/after overalls exactly (0.941 → 0.934, 0.941 → 0.9375), and a status read off the acceptance file must then also say 0.941. No serving number is claimed; the bar is one definition, everywhere, retro-consistent.
- **kill test:** If any historical cycle's recorded overall cannot be reproduced from its own section scores under the pinned set, the recorded headline was never a mean of its sections — stop, report the discrepancy as the finding, and do not ship a definition that rewrites history silently.

### HV-006 · Registry discipline: make the book replayable — byte vault + lineage-complete rebuild for every adoption path
- **source:** `factory/registry.json` is 1,014 lines rebuilt wholesale by `factory/registry.py` `build_registry()` from a filesystem scan plus `battery_evidence.json`; `factory/lineage.jsonl` holds 72 lines and cannot reconstruct it. The cost of that gap is already paid twice: both repair records document a negative full-VM copy hunt — REPAIR-cycle-006 ("No surviving copy of either file exists on this VM… Rebuild was the only path") and REPAIR-cycle-007 ("no surviving copy of either byte string exists"). The cycle-006 fix (`growth_cycle.py` `_snapshot_model_files()`) snapshots bytes only inside growth cycles; widen, dream, assembly, and niche-expansion adoptions still write model files with no byte snapshot anywhere.
- **mechanism:** One adoption helper every path must pass through: before any model file is overwritten or a registry entry changes role, the prior bytes are copied into a content-addressed vault (named by sha256, so identical bytes cost one copy) and a lineage event records (artifact, old sha, new sha, gate evidence). `build_registry()` then gains a replay mode: reconstruct the book from lineage alone and diff it against the scanned book.
- **change:** `factory/registry.py` `write_registry()` / `build_registry()` — vault write + replay mode; `factory/growth_cycle.py` `_snapshot_model_files()` / `_restore_model_files()` generalised into the shared helper the widen/dream/expansion executors (`factory/executors.py`, `factory/dream.py`, `factory/niche_expansion/expansion_cycle.py`) call; `factory/audit.py` `full_audit()` gains the replay-diff check.
- **judged by:** Replay test: lineage-replayed registry must equal the scanned registry byte-for-byte on entries and shas, and a deliberately deleted serving file must be restorable from the vault to its recorded sha256 (the exact operation both 2026-11-12 repairs could not perform). Process bar, stated as such; serving numbers untouched.
- **kill test:** If replay cannot reproduce the current book from the lineage that exists today, do not backfill by hand-writing history — ship the vault prospectively only, and record replayability as starting from the first vaulted adoption, not as a property of the existing book.

### HV-007 · Lineage discipline: a mandatory per-class before/after scorecard on every state-changing record

Non-cycle ledger entries get their own kind namespace so cycle parsing never shares a stream with announcements.

- **judged by:** Retro-computability test: re-running the e007 analysis using *only* records written under the new schema (simulated on the cycle-007 record, which is nearly complete) must answer every question e007 marked "cannot tell from records." Audit bar: zero state-changing records with a missing scorecard field.
- **kill test:** If the cycle-007 record — the most complete on file — cannot be expressed in the schema without inventing values, the schema is asking for data the pipeline never computes; cut it to the fields the pipeline actually produces and retire the rest.

### HV-008 · Failure drill + scoped serving: one corrupt file currently refuses the entire hive
- **source:** `factory/serve.py`'s own contract: at load, `ServingHive.load()` runs `factory/audit.py` `verify_files()` over *every* registered entry (`audit.py` `_entries()` — serving, fallbacks, shadows, substrates, payloads, all 16 composition members) and "an unverified artifact does not serve, and neither does anything else through a tainted book." A bit-flip in a never-served shadow or an old fallback therefore takes down all 7 niches plus the composition — maximum blast radius, and it has never been drilled: no record shows a fault-injection run against the serving path.
- **mechanism:** Drill first, then scope the failure: a fault-injection suite on a *copy* of the lab (flip one fallback byte; delete the shadow; corrupt `learned_say.json`; truncate the serve log) records which faults refuse everything vs fail gracefully — the say-state path already degrades gracefully, the file audit does not. Then move verification to per-entry laziness: `ServingHive._model()` verifies the entry it is about to serve, so a tainted fallback blocks only its own niche's fallback path while verified niches keep serving; the load-time full audit remains as the strict mode for battery runs.
- **change:** `factory/serve.py` `ServingHive.load()` / `_model()` — lazy per-entry verification with the strict load audit kept behind the existing battery path (`factory/run_battery.py` unchanged as judge); drill suite as a new file under `factory/tests/` following `test_growth_cycle_rollback_paths.py`'s pattern.
- **judged by:** Drill scorecard: with a fallback corrupted in the copy, the other 6 niches + composition must still answer and the affected niche must fail closed (never serve the corrupt bytes); with a *serving* artifact corrupted, that niche refuses and the rest serve. Serving numbers unchanged by construction — the battery must still read 0.941 overall with sealed 0.8611 under strict mode.
- **kill test:** If the drill shows lazy verification lets any corrupted artifact actually answer a call (a single wrong-sha model served), the scoping is unsafe — retire it, keep the drill, and keep all-or-nothing load as the recorded, deliberate choice.

### HV-010 · Growth cron scheduling: signal-gate the ~6h cycle — it trains on a clock, not on evidence
- **source:** The `hive-growth-cycle` cron fires on a fixed `interval@6h` regardless of what changed. The ledger shows what that buys: cycle 004 (2026-11-12 06:50 UTC) and cycle 005 (12:50 UTC) each birthed both targets with the battery flat at 0.941 → 0.941; cycle 006 fired ~6h later (18:52 UTC) and regressed it (0.941 → 0.934, audit failed). Meanwhile `factory/growth_cycle.py` `preflight()` — "the cron decision, without running anything" — checks only the lock (`_lock_blocker()`) and lab busyness (`_lab_busy_jobs()`): a cycle with zero new evidence since the last one runs the full train/gate/battery spend anyway, and every run spends the sealed battery twice (before/after via `measure_served_battery()`).
- **mechanism:** Add an evidence-mass term to the skip decision the runner already knows how to make (`_skip_cycle()` is a normal, silent outcome): new serve-log lines since the last cycle, thermostat movement in `factory/dream_state.json`, and a changed mined-target ranking must clear a floor before a full cycle is worth its sealed spend; below the floor the invocation skips with a ledger line naming the missing signal. The cron schedule itself is untouched — the gate lives where the skip already lives.
- **change:** `factory/growth_cycle.py` `preflight()` — compute and record the evidence-mass terms alongside lock/busy; the cycle entry points (`run_cycle` / `run_cycle2` / `run_cycle3`) honour a below-floor verdict through the existing `_skip_cycle()` path.
- **judged by:** Process measures, labelled as such: idle-skip rate across the next 10 invocations, and zero false skips — a skipped invocation followed within one cadence by a forced cycle that produces a kept birth proves the floor miscalibrated and is reported as such. Serving bar unchanged: any cycle that does run must still end ≥ 0.941 with audit clean.
- **kill test:** If two consecutive signal-skips are each followed by a forced run that births, the evidence-mass terms do not predict trainability — retire the gate and return to clock-only firing, with the negative result in the ledger.
