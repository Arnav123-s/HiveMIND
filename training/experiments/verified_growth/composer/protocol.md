# Plan selection from English request and supplied table

Give each arm the exact same user request and table. The solver never receives a task name, plan, family label, key or external grade. A tiny classifier selects count or sum and independently selects a scalar, grouped mapping, or high/low group name. Train using the checked-in English examples, with no filtered grouped requests and no lowest-sum request. A flat classifier selects only whole operation pairs that appeared in training. A simpler handwritten planner, single-operation cap and grammar-restricted native t80 selector are matched arms. Each shares the identical field binding, type checks, executor, filter grounding and refusal policy. These common steps are human-authored. The native model sees only the exact request and headers. It chooses operations; it does not generate or evaluate Python. The SQLite grader was independently written and frozen before evaluation. Score exact values, wrong answers, abstentions and both table variants together per prompt. A valid program alone cannot establish that the user wanted it.

Positive examples span unfiltered count, sum, grouped count, grouped sum, greatest count, least count and greatest sum, plus filtered scalar count/sum. Exact operation identities, parameters and any qualification rules are frozen with the source before unlocking held-out outputs. None of the development requests comes from the fixed HiveMIND release exam. The independent release evaluator may call the frozen file adapter separately on literal official tasks and measure actual opportunities.

The additional agreement arm releases only when the rule planner and the two learned selectors chose the same operation pair. Intended separate operations are an equality restriction, grouping, summing or counting, and choosing a high/low key. Development smoke cases used plain count/sum, grouped sum, least/greatest count or sum, and filtered count. Lowest sum is absent from classifier training but was inspected in the development smoke panel. No development smoke case involved filtering followed by grouping and an extremum. Two class labels alone cannot show that grounding correctly captured all constraints in a request.
