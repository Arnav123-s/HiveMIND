# Growing the hive through cooperation

Give each cell two abilities. It can perform work, and it can tell another cell what work is still missing. A group that can deliver a checked result should expose the same interface as an individual. This lets a group of three become a specialist that another group can recruit. A simple conversation can still use one speaker and one model call.

The repository already has a working example. The research hive coordinates readers, experimenters and checkers, then returns the same result shape as a single researcher. The grown-weight path has a narrower vocabulary. Its lineage code recognizes four organ names and caps the active body at 24. Its usual seating policy starts with the trunk. Keep the existing organs as useful starting groups and let a cell acquire new capabilities independently of its name. [Research hive](../../../team/specialists/research_hive.py) · [Lineage](../../../training/lineage.py) · [Seating](../../../team/ternary.py)

## Six changes worth testing

1. **Post the missing work with its evidence.** A cell that has measured a sensor can post “I have five readings and need coefficients checked against them.” Attach the goal revision, the readings and a completion check. Any qualified cell may take a short lease on the job. If the owner disappears, another resumes from the last receipt. A calendar write, for example, needs a stable action ID so a replacement can recognize a booking that already happened. The existing per-run board already holds steps, facts, artifacts and events. [Board](../../../team/board.py)
2. **Let peers learn whom to ask.** Each capability advertisement should include a worked example, a known failure, its cost and when it was last checked. Keep referrals local to the kind of evidence and work requested. A child that fails with interaction terms can remain excellent on affine inputs. Give new or substantially changed cells some exploration opportunities. Reserve a cross-group contact for requests the local group repeatedly fails to resolve.
3. **Give credit to a useful handoff.** In the CPU experiment the child gathered enough information on all four interaction sensors, then its chosen code peer failed all four. Scoring only the final answer would mark the measurement skill as worthless. Replay the same saved evidence through another helper. When one pairing repeatedly unlocks a verified result, remember that pairing. Teach another group the procedure, its check and the counterexamples where it fails. [CPU outcomes](README.md)
4. **Let useful groups become cells.** A recurring measurement, fitting and checking team can advertise a single calibration capability. Its caller supplies one goal and receives one verified result. Internally the group can recruit different members as the problem changes. When nobody can handle a recurring request, save its failed cases. Use idle CPU time to try new combinations, then offer the new skill to other groups once it passes fresh cases. Split an overbroad specialty when different subgroups demonstrably succeed on different cases. Keep a rare specialist dormant until another member can pass the cases that distinguish it. The existing spawn loop discovers repeated small decisions at individual call sites. Sequences of successful handoffs are the next place to look. [Existing spawn loop](../../../team/cells/spawn.py)
5. **Keep the user's goal coherent.** Give each conversation one current record of corrections, commitments and open questions. Any available speaker can use it. If the user changes a train arrival from 4 to 6, the scheduler must reconsider the pickup time. The file reader can keep its earlier verified work. Record which facts each result depended on so the correction reaches the right cells. Several workers repeating one source still contribute a single piece of evidence. A disagreement is a reason to seek a distinguishing observation.
6. **Grow the archive while budgeting each task.** Pass remaining CPU time, wakeups and deadline down the chain. A parent divides its allowance among children so recursive groups cannot multiply the same budget. Keep a small resident set and index dormant capabilities. The CPU experiment exercised a catalog of 26 with two resident adapter slots. If lookup traffic concentrates on one peer, cache or replicate its directory entries. If a request attracts many weakly matched candidates, improve its description or split the specialty.

## A routing replay

I replayed the trained child's four saved interaction notebooks, with a limit of four worker contacts per task. Exactly one matching worker could fit interactions. The others could fit only an affine rule. A public check tested candidate answers against the recorded readings. Eight private predictions graded each final answer. Each notebook was reused with the capable worker at every initial position.

| Registered entries | Workers advertising the requested skill | Fixed order | Referrals updated from public checks |
| ---: | ---: | ---: | ---: |
| 32, 512, 8,192 or 65,536 | 8 | 16/32 | 28/32 |
| 65,536 | 64 | 16/256 | 40/256 |

With eight matching workers, remembering outcomes also reduced total worker contacts from 104 to 56. Unrelated entries were easy to skip because the request supplied a topic. Discovering that topic from ordinary language remains a separate test. Population sizes here count simulated registry entries. The replay used Python procedures and previously measured cell outputs.

The simulated directory gave each directory node two outgoing links. At 1,024 directory nodes a healthy lookup took at most ten hops. When 10% of directory nodes were unavailable, 1,418 of 4,096 lookups reached one designated copy. A second copy raised reachability to 2,278. That test used fixed paths without detours. Directory lookup, backup routes and stale referrals deserve their own failure tests. Run `python -m training.experiments.rule_lab_referrals` from the worktree to reproduce the numbers. [Replay code](../../experiments/rule_lab_referrals.py)

## The next real CPU trial

The smallest implementation is two additional kinds of board record. One records an unmet need and the evidence available to solve it. The other records which peer was tried, the input conditions and the checked outcome. An indexed SQLite lookup can serve these on the current machine. Keep two adapters resident for the first comparison. Physically separate directories when measured contention or recovery requirements justify it.

Give the hive a calendar task that requires a conversation, timetable reading and constraint checking. Introduce a new helper partway through under an opaque ID with worked examples. Change one user constraint, then retire the most-used helper after its first saved action. Compare trunk-first seating, a centralized router that learns from the same receipts, and local peer referrals. Give all three the same examples, tools, verifier, CPU limit and resident memory.

Score the completed calendar, duplicate writes, CPU seconds, model wakeups and time to discover a replacement. Add unrelated specialists and repeat. Then add plausible but differently skilled specialists and repeat. The larger hive should retain the cost and responsiveness of an ordinary interaction while gaining tasks it can complete through new combinations.
