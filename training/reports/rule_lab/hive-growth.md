# Growing the hive through cooperation

Give each cell two abilities. It can perform work, and it can tell another cell what work is still missing. A group that can deliver a checked result should expose the same interface as an individual. This lets a group of three become a specialist that another group can recruit. A simple conversation can still use one speaker and one model call.

The repository already has a working example. The research hive coordinates readers, experimenters and checkers, then returns the same result shape as a single researcher. The grown-weight path has a narrower vocabulary. Its lineage code recognizes four organ names and caps the active body at 24. Its usual seating policy starts with the trunk. Keep the existing organs as useful starting groups and let a cell acquire new capabilities independently of its name. ## The life of a cell

A newborn belongs from its first turn. Give it an identity, a parent, its own experiences and recurring time with other members. It may start from inherited weights, learn from a neighbor, or bring a different model behind the same work interface. Even a child that never becomes good at a particular task can live a long time and have children. Task feedback changes which answers the body relies on and which peers it asks for help.

Let births happen individually as adults have time and the hive can support another member. As the CPU gets crowded, slow births and share waking time. A sleeping cell keeps its relationships, memories and place in the rotation. Death is a rare individual event whose probability can rise gradually with age. Death ends that identity. Whatever it shared can outlive it, and unshared experience can genuinely be lost. Parents, children and grandchildren can work alongside each other.

What makes the collection one body is a shared goal, a record of its commitments and a way for one cell's observation to change another's next action. For example, if a cell gathering measurements dies, the next cell can read its observations, propose an answer and finish the same request. Individual cells can disagree or make mistakes while the body checks what it returns to the user. On a single CPU, keep a census of living identities alongside a much smaller list of models currently loaded for work.

## Six changes worth testing

1. **Post the missing work with its evidence.** A cell that has measured a sensor can post “I have five readings and need coefficients checked against them.” Attach the goal revision, the readings and a completion check. A cell can claim a turn, ask a neighbor for help or post a partial result. If the owner disappears, another resumes from the last receipt. A calendar write, for example, needs a stable action ID so a replacement can recognize a booking that already happened. The existing per-run board already holds steps, facts, artifacts and events. [Board](../../../team/board.py)
2. **Let peers learn whom to ask.** Each capability advertisement should include a worked example, a known failure, its cost and when it was last checked. Keep referrals local to the kind of evidence and work requested. A child that fails with interaction terms can remain excellent on affine inputs. Protect a rotation for every living member, including those with a long string of misses. Reserve a cross-group contact for requests the local group repeatedly fails to resolve.
3. **Give credit to a useful handoff.** In the CPU experiment the child gathered enough information on all four interaction sensors, then its chosen code peer failed all four. Scoring only the final answer would mark the measurement skill as worthless. Replay the same saved evidence through another helper. When one pairing repeatedly unlocks a verified result, remember that pairing. Teach another group the procedure, its check and the counterexamples where it fails. [CPU outcomes](README.md)
4. **Let useful groups become cells.** A recurring measurement, fitting and checking team can advertise a single calibration capability. Its caller supplies one goal and receives one verified result. Internally the group can recruit different members as the problem changes. When nobody can handle a recurring request, save its failed cases. Use idle CPU time to try new combinations, then offer the new skill to other groups once it passes fresh cases. Parents and offspring can both teach it and go on to develop different interests. The existing spawn loop discovers repeated small decisions at individual call sites. Sequences of successful handoffs are the next place to look. [Existing spawn loop](../../../team/cells/spawn.py)
5. **Keep the user's goal coherent.** Give each conversation one current record of corrections, commitments and open questions. Any available speaker can use it. If the user changes a train arrival from 4 to 6, the scheduler must reconsider the pickup time. The file reader can keep its earlier verified work. Record which facts each result depended on so the correction reaches the right cells. Several workers repeating one source still contribute a single piece of evidence. A disagreement is a reason to seek a distinguishing observation.
6. **Budget waking time as the population grows.** Pass remaining CPU time, wakeups and deadline down the chain. A parent divides its allowance among helpers so recursive groups cannot multiply the same budget. Keep a small resident set and index dormant capabilities. The CPU experiment exercised a catalog of 26 with two resident adapter slots. If lookup traffic concentrates on one peer, cache or replicate its directory entries. If a request attracts many weakly matched candidates, improve its description or split the specialty.

## A routing replay

I replayed the trained child's four saved interaction notebooks, with a limit of four worker contacts per task. Exactly one matching worker could fit interactions. The others could fit only an affine rule. A public check tested candidate answers against the recorded readings. Eight private predictions graded each final answer. Each notebook was reused with the capable worker at every initial position.

| Registered entries | Workers advertising the requested skill | Fixed order | Referrals updated from public checks |
| ---: | ---: | ---: | ---: |
| 32, 512, 8,192 or 65,536 | 8 | 16/32 | 28/32 |
| 65,536 | 64 | 16/256 | 40/256 |

With eight matching workers, remembering outcomes also reduced total worker contacts from 104 to 56. Unrelated entries were easy to skip because the request supplied a topic. Discovering that topic from ordinary language remains a separate test. Population sizes here count simulated registry entries. The replay used Python procedures and previously measured cell outputs.

The simulated directory gave each directory node two outgoing links. At 1,024 directory nodes a healthy lookup took at most ten hops. When 10% of directory nodes were unavailable, 1,418 of 4,096 lookups reached one designated copy. A second copy raised reachability to 2,278. That test used fixed paths without detours. Directory lookup, backup routes and stale referrals deserve their own failure tests. Run `python -m training.experiments.rule_lab_referrals` from the worktree to reproduce the numbers. ## A population with overlapping lives

I simulated 32 populations, each starting with 12 founders, for 300 ticks with two work turns per tick. A child joined the ordinary rotation at birth. Adults were equally eligible to have a child from age 12. Each tick had at most one birth opportunity, which became less likely as the rotation filled and paused at 80 living members. That setting leaves enough turns for every member once per 40 ticks. A child inherited its parent's procedural type, with a 25% chance of drawing a type anew. Even the weakest type submitted its own proposals, an out-of-range measurement or an incorrect constant rule. Individual deaths could start at age 40, with illustrative per-tick probabilities of 0.02% and, from age 180, 0.06%. A tick is a simulation step. These rates are choices for this trial.

Across the 32 populations there were 1,493 births and 107 deaths. The final populations ranged from 48 to 63 members. Of the living children, 671 had taken a turn and never contributed a usable reading or answer. Of those, 268 had themselves had children. Twenty-seven cells died after previously giving a correct answer. Another 77 living newborns were still waiting for their first turn when the trial ended. In a paired replay I disabled every correct final answer. All 32 histories had exactly the same births, parents, deaths and event times.

For the shared task, one procedural cell posted a saved sensor notebook and a different cell had to interpret it. Three simulated tasks finished after the reader had died. These were repeated replays of four notebooks. The population trial measures scheduling, survival and continuity.

I also ran two fresh sensors on the real CPU model. On sensor 331, the data cell saved four readings. I then closed its private worker and removed its identity from duty for the rest of the drill. The code cell proposed an answer contradicted by a reading. The trained child used the same notebook to finish. On sensor 332, the code cell that had been wrong took the four measurements, and the trained child finished again. Both tasks passed all eight hidden predictions, with no repeated measurements. This drill used three adapters on one shared base with scripted duties and a deliberately scheduled loss. Long-horizon learning by populations of different base models is an open experiment.

## The next real CPU trial

The smallest implementation is two additional kinds of board record. One records an unmet need and the evidence available to solve it. The other records which peer was tried, the input conditions and the checked outcome. An indexed SQLite lookup can serve these on the current machine. Keep two adapters resident for the first comparison. Physically separate directories when measured contention or recovery requirements justify it.

Give the hive a calendar task that requires a conversation, timetable reading and constraint checking. Introduce a new helper partway through under an opaque ID with worked examples. Change one user constraint and stage the loss of a busy helper after its first saved action. Compare trunk-first seating, a centralized router that learns from the same receipts, and local peer referrals. Give all three the same examples, tools, verifier, CPU limit and resident memory.

Score the completed calendar, duplicate writes, CPU seconds, model wakeups and time to discover a replacement. Add unrelated specialists and repeat. Then add plausible but differently skilled specialists and repeat. The larger hive should retain the cost and responsiveness of an ordinary interaction while gaining tasks it can complete through new combinations.
