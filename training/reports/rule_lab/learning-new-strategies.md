# How the CPU hive could learn its next strategy

The long-term target is a hive that can accept an unfamiliar assignment, decide what it needs to learn, deliver the work and use the experience on a different assignment. The first capability I would invest in is **choosing the next experiment when all available workers make the same mistake**. A cheap experiment can reveal which part of a program to rewrite, which measurement a scientist needs, or which question to ask a user. A growing hive can inherit both the method and the test that distinguishes when it applies.

## What the current hive was missing

I compared frozen programs case by case. For each input I counted a success if *any* submission was correct, even if a deployed hive had no way to select it. The five first submissions came from g41, two 4B models and the 3B and 7B coders. Three had confirmation runs. The counts below come from the version-2 grades at commit `3b8b46a`. [Field-work evidence](fieldwork/evidence.json.gz) · [Coverage calculation](../../experiments/fieldwork/strategy_coverage.py)

| Task and split | Cases | Best single first submission | Covered by any first submission | Covered after adding three archived public variants |
| --- | ---: | ---: | ---: | ---: |
| Roster, primary | 73 | 29 | 29 | 29 |
| Ferry, primary | 73 | 46 | 46 | 46 |
| Roster, confirmation | 49 | 16 | 16 | 17 |
| Ferry, confirmation | 49 | 37 | 37 | 38 |

On the primary ferry set, 28 trips were unreachable and 18 had a fastest route that could skip the pass. The first submissions covered all 46. They missed **all 27** where using the pass was essential, and all 12 such confirmation cases. The 7B code stored the pass flag but tested the ordinary layover before admitting either boarding option. On the roster, the first submissions covered only one of ten primary cases with tied optimal schedules. Routing alone could recover zero extra primary cases from these fixed outputs. Generating, repairing or combining code changes the pool and can change that result. The three additional conditions were the 4B public retry, its school-and-retry run and the 7B run with reference notes. [Contracts and graders](../../experiments/fieldwork/PROTOCOL.md)

## Can one counterexample change what a worker does?

I gave the local Qwen2.5-Coder-7B the original ferry contract, its earlier program and three executions with independent answers. One arm saw the first three ordinary public examples, including one already in the contract. The other saw three versions of the same two-leg trip. With no layover the right answer was `[10, 0]`. Changing only the first or the second stop's layover made it `[10, 1]`. The parent returned `[16, 0]` in both cases. Each arm had one greedy rewrite, seed 3141, four CPU threads and a 1,000-token ceiling. I designed the probes after seeing the earlier failure. The ordinary set exposed one wrong output and the matched set exposed two.

Both replies reproduced the parent's source byte for byte. Each earned **32/48** on newly generated small graphs. All 16 trips that needed the pass failed. I then tried a fresh context for each feedback set. The new worker saw the parent's outputs and the same checked examples, with the source and prior assistant turn omitted. The original trial and this follow-up were each specified before their respective drafts were scored. All four drafts used pretrained weights. The model received no hidden labels or algorithm templates. [Trial design](../../experiments/fieldwork/PROTOCOL.md) · [Frozen responses and grades](fieldwork/strategy-feedback.json)

| Frozen program | Fresh graphs / 48 | Of those, pass essential / 16 | Earlier exam / 73 | Earlier confirmation / 49 | Large cases / 2 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Original 7B | 32 | 0 | 46 | 37 | 0 |
| Rewrite with ordinary feedback | 32 | 0 | 46 | 37 | 0 |
| Rewrite with matched feedback | 32 | 0 | 46 | 37 | 0 |
| Fresh context, ordinary feedback | 17 | 0 | 41 | 28 | 0 |
| Fresh context, matched feedback | 10 | 0 | 18 | 15 | 0 |
| Earlier worker with supplied algorithm family | 48 | 16 | 73 | 49 | 2 |

The fresh contexts produced different programs. Neither added a correct case beyond the parent on any of the three sets. The fresh matched program even started at stop zero when the request named a different origin. The study gives a concrete reason to try a **small independently testable edit**. Preserve the part that already routes ordinary trips and let a child propose and test the condition that decides whether boarding is allowed. Have a separate test designer try to break the revised behavior. On a genuinely new task the hive must locate that boundary itself. A weak child can still have value elsewhere or contribute a fragment, as the geology worker did.

The 48 new graphs contained 16 unreachable trips, 16 where the pass was unnecessary at the optimum and 16 where it was essential. A separate exhaustive enumeration of timed boarding states agreed with the reference on all 48 labels and all six feedback examples. The two large cases are already included in the exam and confirmation columns. This was one model, one decoding seed and one diagnosed rule. The matched trip was human-designed, the follow-up was prompted by the first result, and prompt lengths differed. Testing the effect of giving a child its parent's code now requires other rule families, models and orders of presentation.

## How growth could compound

1. **Give a worker the ability to challenge its own explanation.** Have it propose two possibilities and a cheap observation that would distinguish them. Also let it vary one condition in an example when all workers agree. In code, a slow exhaustive solver on tiny inputs can label the experiment independently. In science, use a measurement with a prediction recorded beforehand. In conversation, ask the user when two plausible interpretations would lead to materially different actions. Save the prediction, observation and revision. FunSearch found new programs by coupling proposals to a trusted evaluator. Box’s Loop found improvements to statistical models by iterating between proposing and criticizing them. Both depended on informative feedback. [FunSearch](https://deepmind.google/blog/funsearch-making-new-discoveries-in-mathematical-sciences-using-large-language-models/) · [Box’s Loop](https://proceedings.mlr.press/v235/li24v.html)
2. **Let a failed cell contribute a working part.** Store a callable fragment with its input contract, what it predicts, an example that previously broke it and the parents needed to rebuild it. Another cell can try that fragment in a new decomposition. Give it credit if removing the fragment breaks a previously unseen job. This matters here. A failed geology submission contributed a useful intake phase, while removing an observatory helper left all 24 easy successes intact. DreamCoder offers a precedent for learning both a reusable program library and a neural policy for searching it. [Local fragment experiments](field-work.md) · [DreamCoder](https://arxiv.org/abs/2006.08381)
3. **Keep rare cells alive while limiting the number working at once.** Give each job one owner responsible for the result. A sub-hive can explore a few different hypotheses and return a prediction, evidence and confidence in a shared notebook. Give newborns trial assignments, move redundant or idle cells into inexpensive storage and revisit rare ones as new tasks appear. Let one group invent challenges just past another's current ability. Keep a challenge when an independent check can score it and learning it later helps on outside work. Track which jobs would fail if a lineage disappeared. POET demonstrated that a solution developed for one simulated challenge can advance another. An empirical multi-agent study also found coordination could hurt sequential planning. Both are reasons to measure when a second cell earns its CPU time. [Enhanced POET](https://proceedings.mlr.press/v119/wang20l.html) · [Agent scaling study](https://arxiv.org/abs/2512.08296)
4. **Teach the small planner from verified experience.** Once search repeatedly finds a working strategy, train a small adapter on which experiment to run and when to consult a specialist. Keep a sample of old jobs, rare failures and cases where the correct decision is to ask for information. Compare the trained and original planner with identical archives, then repeat with the relevant helper hidden to measure what transferred to the weights. For continual reinforcement learning, reward verified outcomes and later reuse. Keep independent tests outside the reward loop. Published RL results differ across training recipes, so track both the delivered answer and whether *any* attempted answer within budget worked. [Expert Iteration](https://proceedings.neurips.cc/paper_files/paper/2017/hash/d8e1344e27a5b08cdfd5d027d9b8d6de-Abstract.html) · [RL with verifiable rewards](https://proceedings.neurips.cc/paper_files/paper/2025/hash/537d5aa768c2d534016a4d06f87bc8fb-Abstract-Conference.html) · [ProRL](https://arxiv.org/abs/2505.24864)

Give the hive a smaller action than “rewrite the program.” Let a proposer invent one intermediate quantity, split one state in two, add one observable or replace one transition. Try several short changes against a trusted small example, minimize the one that exposes the difference, and test surviving changes on untouched cases and large inputs. Keep the language for describing these changes available equally to all contenders. AlphaGeometry illustrates the division of work. A learned model proposed auxiliary constructions while a symbolic engine checked what followed. Its geometry-specific engine and 100 million synthetic examples show the size of the training investment behind that result. For a CPU hive, the first question is whether learning even one new intermediate this way transfers to a second task family. [AlphaGeometry](https://www.nature.com/articles/s41586-023-06747-5)

### Where engrams, telepathy and BitNets fit

For recovery, keep a versioned parent and its weight changes and verify the restored file by hash. For learning across cells, keep the behavior, a revealing counterexample and a replayable test. Two specialists can coexist on a shared parent with separate heads or adapters and a cue for which output is wanted. Try combining their weights only after measuring both original jobs and the difficult cases where their answers differ. The local two-teacher trial demonstrated both behaviors in a small network. The contemporary Engram architecture uses a learned lookup for recurring token sequences. That is a third kind of memory with a different test, the CPU cost and accuracy of repeated lookups. [Local reconstruction and transfer](engrams-and-bitnets.md) · [Engram architecture](https://arxiv.org/abs/2601.07372)

For CPU speed, keep the shared backbone resident, try the cheapest proven callable first, and activate neural specialists for uncertainty or new work. The local scratch BitNet already cut a one-token forward pass from 5.46 to 1.48 ms by moving weight rounding to load time. A custom packed kernel won on a large matrix and lost on a small one. Profile complete jobs before writing another kernel. Compare core-minutes per verified job, peak memory, 95th-percentile latency and correctness at the same population size. Test whether a compact learned message between sub-hives preserves the result when replacing the full notebook. [Local kernel benchmarks](continual-learning-and-speed.md) · [Local communication experiments](hive-telepathy.md) · [BitNet CPU report](https://arxiv.org/abs/2504.12285)

To test whether a larger body actually helps, vary the archive from 32 to 128 to 512 eligible specialists. Keep the active slots and CPU budget fixed. Compare against the same number of cloned or shuffled specialists and record successes contributed by rare lineages. Withdraw a frequently used cell, restore it from its engram, then repeat with that snapshot unavailable to measure how much behavior its peers can reconstruct. Track lost capabilities, recovery time and duplicate actions after restart. The existing 4,096-cell experiment used tiny learned numerical cells. The next scaling result should count whole user jobs. [Population and recovery measurements](scaling-the-hive.md)

## What would count as progress over a year

These are proposed experiments and decision points. The timing is a planning estimate.

| Period | Experiment | Decision |
| --- | --- | --- |
| First month | Freeze the initial weights, library and scoring rules. Have an independent author prepare 24 whole jobs across at least eight previously withheld task families, eight jobs each in coding, scientific analysis and instruction following. Keep solutions, family-specific scaffolds and final checks away from the hive. | Establish the current single-worker and hive success rates, including the cost of failed attempts and false declarations of completion. |
| Months 1–3 | Run four conditions on the same jobs and machine. Compare one writer allowed repeated attempts, the current hive selecting from its frozen bank, a hive that can invent experiments and code with the same bank, and that last hive after it has inherited experience from a separate training curriculum. Freeze the inherited bank before the exam and reset job-local state between jobs. | At equal inference budgets, look for at least three additional whole jobs over the strongest baseline, spread across at least two domains. Repeat on independently authored families. A 24-job pilot can justify a replication, and a replication can justify a larger study. |
| Months 3–6 | Repeat growth across three curriculum orders. Give the frozen and growing systems equal development compute. Swap or remove their archives, replay old jobs, then distill successful exploration into a planner and test it with the same tools. | Check whether later generations reach the same quality faster or finish harder jobs. Attribute the gain to inherited tools, learned weights or additional search. Track the worst retained skill and confirm completed jobs independently. |
| Months 6–12 | Take new multi-file maintenance tickets from unfamiliar projects, scientific analyses from people outside the project and multi-turn requests with revisions and interruption. Freeze predictions before future observations arrive. Have independent reviewers reopen delivered artifacts and judge open-ended conversation blind to the system. | Count complete accepted work, uncertainty calibration, corrections honored and CPU cost. Require repeat outcomes across releases and new task authors before expanding the capability claim. |

Give each condition the same tools, local documentation, CPU quota and up to **60 aggregate CPU core-minutes per job**. Four conditions on 24 jobs cost at most 96 core-hours of online evaluation at that cap. Track training and archive-building costs separately and include them in the cumulative cost per accepted job. A taught algorithm is a useful positive control. Record every human hint, recruited model and task-specific evaluator. Keep families distinct when estimating uncertainty. A hundred inputs to one program measure one job. [ScienceAgentBench evaluation design](https://proceedings.iclr.cc/paper_files/paper/2025/hash/f12b4df26344f3be803c06b555252efe-Abstract-Conference.html) · [SWE-Bench Pro](https://proceedings.mlr.press/v306/deng26f.html)

One coding job could require migrating an unfamiliar file format, preserving old records and resuming after a crash. A science job could give two plausible explanations of a sensor drift, allow one measurement, then score a forecast at a different station and the stated uncertainty. Include a case where the observations cannot distinguish the explanations. An instruction-following job could change a constraint after the hive has started, interrupt the process, and check the actual output for the revision and duplicate actions. For an open-ended conversation, score whether the response used the latest correction and whether independent readers found it clear and appropriate.

Define success for the intended user as well. An interactive conversation needs an acceptable time to a useful first reply. An overnight coding or science job can afford much more search if it produces a reproducible answer. Keep a conventional baseline wherever possible. On the first 120 historical Mauna Loa forecast months, a fixed trend and seasonality model achieved 0.714 ppm pooled RMSE versus 1.007 ppm for the hive's adaptive selector. The 2027 forecast still needs future observations. If the goal is parity with a larger model, have independent judges compare both systems' completed work on the same briefs and publish latency and cost alongside quality. The CPU hive can be evaluated without feeding it any of the reference model's answers. [Earlier forecast study](field-work.md#scientific-work-with-consequences-that-can-be-checked)

If correct proposals exist but the hive submits the wrong one, improve selection and verification. If all candidates fail the same requirement, invest in counterexamples, new representations or additional training evidence. If new generations improve only on familiar families, redirect the curriculum toward transfer. If a single CPU writer matches the growing hive on fresh whole jobs at the same cost, that result should change where the project spends its next month.

## Reproduce the checks

The first command needs only Python and the checked-in archive. The second executes the frozen programs with the WASI Python SDK and Wasmtime. Use the existing field-work instructions to set `SDK` to the extracted SDK directory. To generate all four model replies again, replace `--frozen "$TRACE"` with `--binary "$LLAMA_SERVER" --weights "$CODER7B" --threads 4`. The model, runtime and SDK revisions are recorded with the field workers. [Environment and model files](fieldwork/reproduce.md) · [Probe and grading code](../../experiments/fieldwork/strategy_feedback.py)

```bash
python -m training.experiments.fieldwork.strategy_coverage
TRACE=training/reports/rule_lab/fieldwork/strategy-feedback.json
python -m training.experiments.fieldwork.strategy_feedback --sdk "$SDK" \
  --frozen "$TRACE" --out /tmp/hive-strategy-replay.json
```
