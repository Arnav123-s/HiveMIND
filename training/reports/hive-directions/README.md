# How can a CPU hive learn a new skill and still use the old one?

A repair crew asks, “If our electrician is out tomorrow, what can we still finish by Friday?” A useful hive can give the crew a feasible timetable, explain what moved, and revise it when the electrician returns. A growing hive can go one step further. Experience repairing past schedules should help it solve a new kind of disruption, at the same cost, while its original skills still work. That is a concrete open problem for this project.

This report follows the earlier experiments through the G48 record on main (`1414d49`), including changes merged after that generation began. It includes measurements from the actual hive, research prototypes, comparisons with published work, and proposed tests. The shipping and scheduling code here runs separately from the serving and training paths.

For a short read, start with the [missed correct answer and its replay](witness/README.md), the [trade-off in the shipping trials](shipping/second/README.md), and the [five-project scheduling baseline](scheduling/README.md).

## What is already working

The current hive shares an 8-billion-parameter base model, the common set of learned weights that generates text. A **cell** is a small learned change to that model. G48 keeps 24 specialists plus a shared version. Their training overlaps, with extra practice in coding, data, writing or finding information. Some are better at a particular job than others. In ordinary work the hive selects a few, has them try solutions, and compares the results. The solo runner can ask a third member when the first two disagree. A separate store can keep an exact working program and run it again. That is how two methods can coexist even if later training changes a cell. [G48 body](../../../cells/body.json) · [Work routing](../../../team/solo.py) · [Earlier invoice and shipping experiments](../retained-skills/README.md)

Checked file delivery and retaining multiple methods are already on main. The subsequent work added a fixed exam of 30 unseen-by-training jobs and a way for chat to call saved methods when the bank and its runtime are configured. Ordinary chat first decides whether a message needs work. Automatically promoting programs from practice and enabling the bank in the hosted chat workflow are identified as open in the main handoff. The G48 exam ran on older code, so its scores cannot establish the effect of those merged changes. [Delivery and retention](https://github.com/Arnav123-s/HiveMIND/pull/105) · [Fixed exam](https://github.com/Arnav123-s/HiveMIND/pull/106) · [Chat reuse](https://github.com/Arnav123-s/HiveMIND/pull/107) · [Handoff](../../../NEXT_SESSION.md)

## What the measurements change

### A correct cell can lose the vote

We matched the parent and child's 64 task IDs, prompt hashes and grades across 16 original exam archives. Each of eight groups contained four easy and four hard tasks. Both bodies delivered all 32 easy answers. The 32 hard jobs broke down as follows.

| Question | Parent | G48 |
|---|---:|---:|
| Did any graded member solve the job? | 22/32 | 25/32 |
| Did the user get a correct result? | 21/32 | 21/32 |
| Was a correct member's result withheld? | 1 | 4 |
| Did every recorded member miss? | 10 | 7 |

In G48 one code specialist alone passed two bank-module requests and one parser. A data specialist alone produced the correct percentage-change file. All four final deliveries withheld the file. The same code specialist failed two **other** parser tasks. A permanent “trust the coder” rule would confuse a skill with a guarantee. The 25 is a hindsight ceiling for choosing among the recorded hard-task submissions. Seven hard jobs, including all four held-out jobs, needed a solution outside those passing submissions. The equal 53/64 overall scores also hide three job gains and three losses. [Cases, source archives and replay](g48/G48.md)

This also changes how to interpret learning. All 13 parser lessons passed their own checks and training loss on examples set aside fell from 0.584 to 0.383. Yet the team delivered zero of three parser files. First attempts in practice succeeded on 31/47 familiar task kinds and 7/49 newer ones. Of 520 counted new practice and lesson rows, 217 came from the hive's checked work. The record does not measure how many rows from each source actually reached training. The other development branch had already grouped 42 new-kind first-try misses by cause, including 15 timeouts with an answer already present. Fixing timeouts and training on better examples address different failures. [Generation record](../../../docs/reads/g48.md) · [Branch diagnosis](https://github.com/Arnav123-s/HiveMIND/commit/55fb7b6e3348b9f8a136f9ab325818e5e8ba4d70)

### A correct method can answer the wrong question

With the bank configured, we exercised the normal chat entry, the repository's saved programs and the real WebAssembly interpreter. Six plain shipping and tax cases behaved as expected. On 18 deliberately difficult requests, the path released **12 wrong numbers**, stopped four times without completing the requested task, and handed two requests to the ordinary workers as intended. For example, the two parcels on order 801 weighed 410 g and 820 g. The method received three weights, including 801 g, so it returned 700 cents instead of 520. A request for a conversion also got a shipping charge despite explicitly ruling one out. Two additional dialogue controls checked only where execution would go. Model calls and further work were stopped at those boundaries. These are stress cases written after inspecting the implementation. They establish failure modes, not their frequency in the world. [Cases, observed arguments and reproduction](routing/README.md)

**An independently written test ruled out an obvious fix.** Separate agents wrote and froze 28 fresh requests and a narrow reader that required explicit rounding language. At the point where a work request reaches the bank, the current reader completed 7/14 valid jobs exactly, used wrong arguments on five, and invoked shipping on 10/14 requests that needed something else. Our narrow reader declined **all 28**. It prevented mistakes at the cost of every useful job. An always-decline control exposes that immediately. Each arm used the same saved program, and we checked the complete list of weights as well as the final fee. [First independent trial](shipping/first/README.md)

We then froze a second design and scored it on **30 new requests from a different author**. Wrong shipping calls on 15 unsuitable requests fell from **8 to 0**, and wrong weights on valid requests fell from **3 to 1**. Correctly completed jobs also fell from **9/15 to 5/15**. The new reader missed that “a pair of 224 g packets” means two packets. Neither prototype met the bar for adopting it. A better next design can show the interpreted parcels and ask one focused question when a count or tariff is unresolved. Its success measure must include how many valid jobs the user actually finishes. [Recorded criteria](shipping/second-panel-plan.md) · [Second trial and replay](shipping/second/README.md)

## Three changes to try first

**1. Make each saved method say exactly when it applies.** Alongside its code, keep a short record of the action, accepted units, input limits, output, examples of when it applies and a similar-looking request where it should stay silent. For the shipping program the action is “calculate the depot's fee”, a parcel weight must be a positive whole number of grams, an empty shipment is valid and an order number is a label. Trace each proposed argument back to the words or typed field that supplied it. If one part is unknown, ask for that part or return to ordinary work. Record the scope of each correction. A different client's rounding convention calls for another valid version. A program contradicted by its own stated rule should lose authority for that scope, while its source and counterexample stay in history. If two valid rules predict different answers for the current case, one targeted question can settle which to use.

The next test is to learn these records from successful calls and corrections for **three unrelated methods**, then apply them to separately authored requests. Compare with today's matcher, explicit user selection and a small handwritten reader. Count wrong releases, correct jobs, questions and friction on ordinary chat. A method that declines every job can score well on negatives while delivering nothing. [Saved-method implementation](../../../team/saved.py) · [Learning when to defer](https://proceedings.mlr.press/v119/mozannar20b.html)

**2. Let a dissenting cell ask for one decisive check.** When two candidate programs differ, execute a small input on which they make different predictions. Obtain the expected result from a rule in the user's request, an independent tool, an explicit example or a user answer. If the evidence cannot settle it, preserve the disagreement. For example, an invoice with two 11-cent lines can distinguish two rounding conventions. Agreement by a second copy of the same mistake adds little. The earlier timetable worker already chose an endpoint that separated two rules after 90 observations. The new test is whether the hive can generate and validate that separating example for unfamiliar contracts, with no supplied list of hypotheses. [Prior timetable and geology work](../rule_lab/field-work.md) · [Choosing informative tests](https://arxiv.org/abs/1010.3091) · [Measured correlations among models](https://proceedings.mlr.press/v267/kim25e.html)

Freeze the competing files before comparing procedures. Blind member names and order. Give each policy the same CPU-seconds, tool calls and access to public information. Compare the current vote, a third vote, a cheap generic file check and the new test. Include already-agreed answers and jobs where **every** candidate is wrong. Count additional correct deliveries **and** new incorrect confirmations on fresh families. Keep exam expected answers private. The four reviewed G48 cases can become development examples. We tried four small contract checks on the three archived source attempts for the missed G48 parser. They scored **1/4, 4/4 and 0/4**. The only qualifier had produced the right module and printed **10** in its original run. This took zero new model calls. The evaluation agent wrote the checks before opening the programs and already knew the workers’ grades. This recovers one case retrospectively. Whether a cell can invent equally good checks before seeing outcomes is the next trial. [Original attempts, rules, receipt and replay](witness/README.md)

**3. Have a cell discover its own repair.** The earlier shipping repair improved a model-written program from 4/100 to 100/100 on fresh deliveries. Exactly one human-specified edit was eligible. On a second tariff, the generated program tried to decode input that had already been decoded and missed 100/100. Earlier geology work went further by salvaging the useful first stage of a failed program. Both are foundations for a stronger experiment. [Shipping results](../retained-skills/README.md) · [Recovery of working fragments](../rule_lab/field-work.md)

Give one cell past programs and short failure traces. Let it find repeated operations, turn their differing parts into parameters, and propose a reusable edit with an example that would disqualify it. Let a second cell shrink a failure to the smallest input that still breaks the program. Freeze the learned operations before revealing a new domain. Compare one retry, shuffled traces, random same-size fragments, and fragments discovered from the real histories. Give each arm one model turn and up to eight candidate executions per new job. Count previously unsolved *jobs* restored, damage to correct controls, and whether removing the discovered operation erases the gain. This tests transfer across failures. DreamCoder and LILO show how to learn libraries from programs. Break-It-Fix-It learned compiler-oriented repairs. Extending these ideas to wrong answers from valid programs is the frontier here. [DreamCoder](https://arxiv.org/abs/2006.08381) · [LILO](https://arxiv.org/abs/2310.19791) · [Break-It-Fix-It](https://arxiv.org/abs/2106.06600) · [Executable hypothesis search](https://arxiv.org/abs/2309.05660)

Two other rules tie these experiments together. **Choose teammates by what they add.** Estimate how often a second worker solves tasks the first missed, how often they agree on a wrong result and what the extra work costs. Compare a single worker, escalation on uncertainty and a full team on the same future requests. Dependency-heavy jobs can favor a direct worker. **Measure what the hive actually learns from.** For each checked failure, track the method proposed, examples admitted, examples actually trained on, and later performance with memory on and off. Keep the fixed 30-task exam for regression tracking. Reserve a second, fresh set of whole task families for claims of discovery, since the fixed exam helps select generations. ## A hard public challenge with an ordinary user

**Repair a real project timetable when a scarce person or machine becomes unavailable.** Earlier work already solved weighted interval scheduling on 73/73 and a further 49/49 cases using supplied algorithm families. A project with simultaneous resource limits, dependencies, fixed ongoing work and a mid-project change is a stronger test. The user gets a dated schedule, the jobs that moved and the specific bottleneck. A separate checker can verify the result without trusting the author.

We ran three classical scheduling strategies on five published PSPLIB development projects, each with 30 activities. All 330 constructed schedules passed a separate resource and dependency checker. Trying 64 random priority orders per project reached two of five known optima. Its completion times summed to 247 time units against an optimal total of 238. Even this cheap method sets a real bar. These five cases belong to one family. No hive was scored in this pilot. [Schedules, reference optima and runnable baseline](scheduling/README.md) · [PSPLIB](https://www.om-db.wi.tum.de/psplib/getdata.php?mode=sm)

**The proposed trial.** Hold out entire families and keep published solutions away from the solver. Give all entrants the same existing schedule and disturbance. Freeze started activities. Check every dependency, crew limit and finish time. Compare a simple repair, random multistart, an established solver and the hive at one thread for 10 and 60 seconds. Give the established solver the same initial schedule. Score feasibility first, then finish time, disruption to unstarted work, and total CPU and wait time. Count timeouts. Pair results by underlying project. Distinguish a known capacity calendar, a simulated surprise, and an actual project record. Larger instances have best-known bounds even when nobody has proved an optimum. Real cases need authentic resource records. [Time-varying PSPLIB data](https://www.om-db.wi.tum.de/psplib/newinstances.php) · [OR-Tools baseline](https://github.com/google/or-tools/blob/stable/examples/python/rcpsp_sat.py) · [Ghent real projects and data quality](https://www.projectmanagement.ugent.be/research/data/realdata)

**The transfer test.** Give the hive a different problem, diagnosing an unfamiliar sensor. Earlier thermal work chose informative measurements and fitted coefficients from a supplied set of possible equation terms. Let a cell propose a missing term itself, choose one intervention on which competing hypotheses disagree, then predict a new operating regime. Compare its hypothesis against a fixed-library method, a fitted baseline, random measurements and the same hive with its learned operation removed. Award credit on readings the cells could never see during fitting, subject to the same measurement budget. Scheduling tests real-world usefulness. This second domain tests whether the hive learned a reusable way to investigate an unknown. [Earlier instruments](../rule_lab/field-work.md) · [Sparse identification with a candidate library](https://arxiv.org/abs/1509.03580)

## Decision order

1. **Protect the point where a user's words become program inputs.** Test an independently authored set for several methods, including requests that resemble known jobs but ask for a different action. Report both false releases and useful work lost by declining.
2. **Recover a correct dissenting answer without knowing the answer key.** Preserve frozen member submissions on disagreements, then compare selectors on fresh cases at the same budget. Check for regressions on already successful jobs.
3. **Invest in growing new skill once a cheaper explanation is ruled out.** Require at least one whole new family where a learned operation helps, its removal erases the gain, and previously correct controls still work. Replicate on another family before changing the training loop.
4. **Advance to the scheduling and instrument trials.** Publish useful outputs, classical baselines, old-skill retention and resource cost together. If the ordinary solver wins, it can serve the user today and remain the bar the hive must clear.

One result would bring these ideas together. A cell fails on a new request. Another cell finds an operation nobody supplied. The hive checks and keeps it. A different cell uses it later, and an old task still gets the old correct answer. Each link has a corresponding failure test above.
