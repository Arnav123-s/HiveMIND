# HiveMIND as a whole, at generation 47

**The project already has a working CPU assistant, several ways to grow specialists, and a training loop that carries itself across generations. The biggest immediate opportunity is to recognize when one cell has already done the job correctly.** On a new request, the live hive made both a perfect CSV and a malformed one. It delivered the malformed one. On genuinely unfamiliar task families, the harder problem is still learning a missing method.

I reviewed the public default branch through the g47 record, historical reports and their code, the separate Muse and seed branches, and my CPU experiments. I reran the ordinary talk path locally with the same five released weight edits that the chat workflow selects, checked its actual files, and recounted the generation results. I use “recorded” below for earlier experiments whose full training or model runs I did not repeat. ## What the current body can do

**Conversation.** I told the unmodified local talk service that my notebook was called Copper, then renamed it Juniper, then asked for its current name only. It answered exactly “Juniper.” All three assistant messages were generated live. This checks a real correction across three turns. The conversation mode can keep more history than the work handoff, which forwards only the last four previous messages, each shortened to 700 characters. An older correction can therefore be visible to the speaker and disappear from the worker's instructions. [Live transcript](observations.json) · [Handoff](../../../team/talk.py)

**A whole file job.** I asked for a two-column rainfall CSV in the order Wednesday, Monday, Tuesday, and the total in millimetres. The trunk and data specialist both printed the correct **21**. The data specialist wrote the exact three requested rows. The trunk wrote an extra number on each row, so its Wednesday row was `Wednesday,3,7` under the two-column header `day,mm`. The coordinator declared agreement and delivered the trunk's file after 51 seconds. Reopening the two candidate files and checking just the header and column count would have selected the correct one without another model call. This is one observed job. It demonstrates how a real correct answer can be lost. [Files as read back](observations.json) · [Selection and delivery](../../../team/solo.py)

In a separate controlled test we supplied two programs, ran them through the normal coordinator and inspected the delivered file. One put 12 under East and 4 under West. The other put 4 under East and 12 under West, as required. The coordinator confirmed them and delivered the reversed values. Here even their printed answers disagreed about which number belonged to which station. The code compares sets of values and some words. Public exam graders can independently evaluate an answer, while an ordinary task can finish on that agreement alone. The controlled result demonstrates the failure mechanism. It gives no estimate of its frequency. [Controlled evidence](observations.json) · [Agreement code](../../../team/solo.py#L167)

**A new scientific programming task.** I asked the same hive for an importable Python function that calculates time above a threshold from irregular sensor readings, counts upward crossings, and skips missing readings and long gaps. I fixed 40 checks privately before the run. After 597 seconds the hive reported that it could not confirm an answer, and it delivered no module. Three files remained in worker directories. Their scores were **0/40, 0/40 and 16/40**. The data specialist had correctly handled some upward crossings, including fractional durations. Its function missed time when readings stayed above the threshold or crossed downward. [Exact request, drafts and grades](observations.json) · [Independent checker](../../experiments/whole_hive_review.py)

**Could the author repair its own draft?** I took that function back to its own data specialist, with the same weights and a 700-token allowance per attempt. A plain retry again passed 16/40 and 41/96 on a separate set of correlated sensor traces. Giving it one concrete failure left its calculation identical and added file-writing code that failed during import. The complete returned module then passed 0/40 and 0/96. The first example involved two readings both above the ceiling. We supplied the four-minute answer and withheld the private checks. [Frozen prompts, returned code and scores](observations.json)

I then let a checker try all nine pairs of below, equal and above readings. It automatically found three failures. I showed all three to the same cell, required a function that could be imported, and kept a further 256 tests with fractional readings and timestamps private. The cell reproduced its plain retry byte for byte. It passed 16/40, 41/96 and 190/256. I supplied one missing branch to its original function for segments starting above the ceiling. That repair passed **40/40, 96/96 and 256/256**. Two independent reference calculations agreed on all 392 inputs. The cell contributed usable code and the checker found a productive place to edit. I supplied the change that made it work. These follow-ups called the specialist directly and did not deliver a module through public chat. [Frozen repairs and tests](observations.json) · [Reproduction](../../experiments/whole_hive_review.py)

## What the generation scores measure

At this snapshot the top-level README and session handoff still quote g45. The body manifest and raw ledger already record g47. The dashboard and ledger also disagree on the split of hard cases, for a separate reason explained below.

| Same eight exam seeds | Before g47 | After g47 |
| --- | ---: | ---: |
| All cases | 47/64 | 47/64 |
| Easy cases | 31/32 | 31/32 |
| Hard cases of a kind the hive was taught, recounted | 15/25 | 16/25 |
| Hard cases of a kind withheld from teaching, recounted | 1/7 | 0/7 |

The published g47 report says 14/19 taught and 0/6 withheld after training. Its label reader recognizes literal text in task-generator source code. Eight of 37 hard task generators use named constants and are omitted by that reader. I used each registered generator's offline sample to identify its label, summed the raw grades, and checked that the two groups account for all 32 hard cases before and after. The same check gives g45 **13/22 taught and 0/10 withheld**, where its report says 12/16 and 0/9. For g47 the omission even changes the apparent direction of the taught result. Denominators here are **cases**. The 25 taught cases cover 15 distinct families, ten of which passed at least once. Seven withheld cases cover six families. These small samples cannot establish a general success rate on novel work. [Official read](../../../docs/reads/g47.md) · [Raw ledger](../generations.jsonl) · [Offline recount](../../experiments/whole_hive_review.py)

G47 also got **37/96** practice tasks right on the first try and **25/40** on the timed talk exam. Of the 15 missed talk items, ten timed out and nine of those never started. The conversation test includes routing decisions and supplied histories. The project targets are a taught-hard pass share of 0.78, half of withheld cases, 0.70 on first try, 8/10 on talk, and a three-hour generation. All five are open on g47. The record identifies 219 new checked rows from practice and dreams alongside 330 from hand-written lesson generators. The contribution of each source to weights actually trained is unmeasured. The current promotion rule accepts a tie in total cases. It records talk separately, recognizes only four of the ten withheld families in its older gate statistic, and can accept an empty paired comparison when it classifies it as a founding body. G47 had all eight pairs. Its one extra taught pass and one lost withheld pass show why a preserved total matters less than *which ability* a release gained or lost. ## What my experiments added

In the current app, an **engram** is a small weight edit associated with a past task. The index can retrieve it for a similar task and gives preference to the cell’s relatives. Recall is optional and is off in the default serving path. In my reconstruction experiments, an engram could also be a difference from a parent’s weights, a set of examples, or a checked program. The first can reproduce identical weights if the right parent survives. Examples can teach approximate behavior. A program can repeat a procedure directly. To recover two arbitrary networks exactly, the surviving network and record together must contain enough information to distinguish every possible original pair. Shared structure, an extra record, or tolerance for small errors is what made the successful cases possible. [App memory](../../../team/engram.py) · [Reconstruction evidence](../rule_lab/engrams-and-bitnets.md)

**Telepathy** below means a learned message between cells. **Surgery** means changing selected weights, connections or a part of a program and then measuring the effect. The personality study tested conversational tone and the preservation of facts.

## What I would do first

1. **Check the result the user receives.** Read every candidate's actual deliverables before selecting a winner. Validate column names, field/value associations, units, ordering and requested files. Keep the private checker independent of the proposing cell. Record “some member succeeded” beside “the delivered work succeeded.” The rainfall and coding-school cases give immediate regression tests.
2. **Make generation scores comparable.** Carry a stable task-family ID from the generator into training, evaluation and reporting. Require a sufficient matched sample before declaring a promotion. Keep a fixed untouched transfer set, set a separate tolerance for losing previously useful abilities and compare with the best retained body. Keep timed conversation scores and timeouts visible. Muse's rollback procedure is already a worked example.
3. **Let growth preserve rare contributions at bounded CPU cost.** Separate belonging to the population from occupying a live inference slot. Keep a weak child's callable fragment, its parents and the example that reveals its value. Let sub-hives exchange a claim and a test, and train a small selector only when repeated outside checks show which worker helps. Restore a missing specialist periodically and measure what the body can still deliver.
4. **Budget CPU against completed work.** Keep a reusable prompt prefix per compatible model and adapter. Route a single input vector to the fast packed kernel only where measurements justify it. On a 4,096-by-4,096 matrix our packed operation took 0.540 ms versus 0.738 ms for byte weights. At 768 by 192 the byte kernel won, 0.0100 ms versus 0.0121 ms. Track waiting time, retries and checked completions per CPU-hour alongside token speed. [CPU measurements](../rule_lab/continual-learning-and-speed.md)
5. **Then test discovery.** Give the hive 24 independently authored jobs across unfamiliar coding, physical data analysis and multi-turn instructions. Compare one writer with retries, the current hive, and a growing hive at the same total CPU budget. Score actual files, recorded predictions and honored corrections. When no candidate succeeds, let a cell choose a cheap test to distinguish explanations and propose a small change. Require a second, different task family to benefit before calling the result transferable. ## How to check the review

The g47 repository suite reported **788 passed and one skipped**. The skipped native-kernel check passed separately with a writable compiler cache, covering all 789 collected tests. The earlier run without the official 1.7B tokenizer exposed three lesson-length failures under the fallback estimator. With the pinned tokenizer available, those tests passed. This installation detail matters to reproducing the training-row limits.

The local live tests used a Xeon Platinum 8573C with a four-core quota and 16 GiB memory. I verified the 2.03 GiB backbone and all five released adapters against their published hashes. The adapters together occupy about 223 MiB on disk. The executable was the repository's pinned ik_llama.cpp revision `7aa7e01`. The tests used the default talk router and coordinator with the GitHub talk workflow's members. The scientific checker ran separately from the solver. The observations file contains the actual conversation, all three rainfall files, the controlled example and the frozen coding outputs.
